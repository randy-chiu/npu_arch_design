# Transformer Workload Integration Design

## 1. Target / 目标

The goal is to add Transformer workload evidence to the existing NPU
architecture evaluation loop without changing the current NPU core
implementation first.

目标不是马上新增 Transformer 专用硬件模块，而是先建立一条可复用、可审计的
Transformer workload 生成和 PPA 验证路径：

```text
Transformer 原始 workload 规格
  -> deterministic input / weight / golden 生成
  -> firmware 可执行的 NPU descriptor jobs
  -> generated workload_manifest.json
  -> SoC RTL simulation
  -> firmware-read perf CSR snapshots
  -> perf.json
  -> ppa_proxy.json / HTML report
  -> 决定下一步硬件扩展
```

CNN/MNIST 现有路径保持不变，继续作为 SoC、firmware、wrapper、data mover 和
K-stream matmul 的兼容回归。Transformer 新增的是 workload、测试输入、golden、
manifest metadata 和 PPA 输出，不 fork NPU core/wrapper/perf/PPA 框架。

## 2. Overall Design / 整体设计思路

There are three different data levels, and they must not be mixed.

### 2.1 Source Workload Spec / 原始 workload 信息

The first Transformer source of truth is a checked-in workload specification:

```text
workloads/manifests/transformer/transformer_micro_v0.jsonc
```

This file describes logical Transformer micro workloads, for example:

```text
prefill projection GEMM:
  scenario: transformer_prefill
  op: matmul
  logical shape: M x N x K
  precision: int8 activation, int8 weight, int32 accumulator

decode skinny-GEMM m8_compat:
  scenario: transformer_decode
  op: matmul
  logical shape: M=8 current-array-compatible approximation, N x K
  precision: int8 / int8 / int32

KV-cache traffic:
  scenario: transformer_decode
  op: memory_traffic
  logical bytes/token model
```

This source spec is hand-authored initially. It is not generated from an
external LLM model yet. Later, trace-driven manifests may be generated from
model configs or captured traces, but that is not the first milestone.

第一阶段先手写小型、确定性的 micro workload spec。这样可以先验证架构评估链路，
避免一开始就引入大模型权重、tokenizer、trace capture、外部数据下载等变量。

### 2.2 Generated Executable Fixtures / 生成可执行测试数据

A new Transformer fixture generator will read the source spec and produce
deterministic hardware-facing data.

Planned source code:

```text
sw/tools/transformer/
  generate_transformer_micro_fixtures.py  # reads transformer_micro_v0.jsonc
  golden.py                              # integer golden helpers: matmul, traffic model
```

The generator emits or returns:

```text
INT8 activation/input tiles
INT8 weight tiles
INT32 expected output tiles
logical-shape metadata
external/KV-cache traffic metadata
firmware job definitions
```

The generated data must be deterministic:

- fixed integer patterns or fixed seed;
- no external model download;
- no floating-point model dependency for the first milestone;
- shapes small enough for current firmware ROM/SRAM/runtime constraints.

### 2.3 Generated Firmware And Manifest / 生成固件数据和报告语义

The current production manifest is generated by:

```text
sw/tools/firmware/emit_soc_cpu_smoke_data.py
```

The first implementation should keep one production manifest:

```text
build/perf/workload_manifest.json
```

and one firmware data surface:

```text
build/firmware/soc_cpu_smoke_data.h
```

The recommended first implementation is:

```text
emit_soc_cpu_smoke_data.py
  -> calls sw/tools/transformer/generate_transformer_micro_fixtures.py helpers
  -> appends Transformer C arrays / constants
  -> appends Transformer JOB_ID_* values
  -> appends Transformer entries to build/perf/workload_manifest.json
```

This keeps the key rule intact:

```text
the same generation path decides firmware jobs and report semantics
```

If Transformer data grows too large later, we can split generated headers:

```text
build/firmware/soc_cpu_smoke_data.h
build/firmware/transformer_micro_data.h
```

but the production manifest should still be combined unless there is a clear
reason to run Transformer as a separate firmware app.

`emit_soc_cpu_smoke_data.py` is the app-level aggregation point for the
`soc_cpu_smoke` firmware. It should not become the place where Transformer
math, tiling, or traffic modeling is implemented. Domain-specific generation
belongs in domain tools, and the firmware-data emitter only merges their output
into one C header and one production manifest.

当前 `emit_soc_cpu_smoke_data.py` 的职责应定义为 `soc_cpu_smoke` 这个 firmware
app 的聚合器：合并 smoke/CNN/Transformer 的生成结果，写出一个固件 header 和
一个 `workload_manifest.json`。Transformer 的数学 golden、tiling、traffic
model 不应直接写进这个文件，避免和已有 CNN 验证逻辑混在一起。

The existing CNN helper code currently lives in historical paths such as:

```text
sw/tools/npu_phase0/real_mnist_cnn.py
sw/tools/npu_phase0/digits_classifier.py
```

That code does not need to move before Transformer work begins. A later cleanup
may introduce:

```text
sw/tools/cnn/generate_mnist_cnn_fixtures.py
```

but only if it reduces duplication or makes ownership clearer. The Transformer
path should start in `sw/tools/transformer/` so new code is not added to the
legacy CNN helper modules.

## 3. Key Implementation Details / 重点细节

### 3.1 What The Initial Transformer Workloads Are

The first executable workloads should use only current RTL-supported matmul
behavior.

| Workload | Source shape | RTL mapping | Why it matters |
| --- | --- | --- | --- |
| `transformer_prefill_projection_gemm_tiny` | logical GEMM, e.g. `M=128,N=256,K=256` or smaller reviewed shape | tiled into current `8x8x8` matmul / K-stream jobs | prefill projection has high matrix utilization |
| `transformer_decode_skinny_gemm_m8_compat` | logical skinny GEMM with `M=8` current-array-compatible shape | tiled into current `8x8x8` array-compatible jobs | decode exposes low batch/token pressure without adding true GEMV hardware yet |
| `transformer_decode_kv_cache_traffic_tiny` | bytes/token model | model-only initially, no RTL descriptor required | makes decode external-memory pressure visible in PPA |

The earlier word `proxy` meant "a substitute workload that approximates the
pressure of a not-yet-supported operation using current RTL-compatible shapes."
For decode, the real LLM operation is often single-token GEMV or very skinny
GEMM. Current RTL has an `8x8` matrix array, so the first executable decode
workload uses `M=8` and is named `m8_compat` to make the compatibility
constraint explicit. It is not a true single-token GEMV implementation.

这里的旧词 `proxy` 不是指软件代理或硬件代理模块，而是“在真实 GEMV/skinny decode
硬件还不存在时，用当前 RTL 能执行的形状近似这个场景的压力”。为避免歧义，设计
命名改成 `m8_compat`：表示它是当前 `8x8` array 兼容的 decode 近似 workload，
不是最终的单 token GEMV。

### 3.2 How Logical Shapes Become Current RTL Jobs

Current RTL supports fixed `8x8x8` matmul tiles and K-streaming accumulation.
Therefore a logical Transformer GEMM becomes many descriptor jobs or K-stream
jobs.

Example:

```text
logical GEMM: M x N x K
tile shape:   8 x 8 x 8

M tiles = ceil(M / 8)
N tiles = ceil(N / 8)
K chunks per output tile = ceil(K / 8)
```

For each output tile:

```text
generate A tile stream over K chunks
generate B tile stream over K chunks
compute expected int32 C tile
emit one MATMUL_K_STREAM descriptor when using existing K-stream path
```

The generated manifest should not duplicate full shape metadata on every tile.
Tile jobs should carry small identity fields:

```json
{
  "job_id": 69,
  "workload": "transformer_prefill_projection_gemm_tiny",
  "op": "matmul_k_stream",
  "role": "transformer_micro",
  "tile_id": 0
}
```

The workload-level metadata should carry the logical details once:

```json
{
  "kind": "transformer_micro",
  "metadata": {
    "scenario": "transformer_prefill",
    "logical_op": "projection_gemm",
    "logical_shape": {"m": 128, "n": 256, "k": 256},
    "rtl_tile_shape": {"m": 8, "n": 8, "k": 8},
    "precision": {
      "activation": "int8",
      "weight": "int8",
      "accumulator": "int32"
    },
    "activity_scope": "kernel_only",
    "external_memory": {
      "activation_read_bytes": 32768,
      "activation_write_bytes": 32768,
      "weight_read_bytes": 65536,
      "kv_cache_read_bytes": 0,
      "kv_cache_write_bytes": 0
    }
  }
}
```

### 3.3 What Firmware Executes

Firmware should gain a separate Transformer section after the existing smoke
and CNN regressions:

```text
operator smoke
digits/CNN compatibility workloads
Transformer micro workloads
final status write
```

For each executable Transformer tile job, firmware should:

1. stage generated input/weight/program/descriptor data in SRAM;
2. launch the existing NPU wrapper descriptor;
3. wait for completion;
4. compare output SRAM against generated INT32 golden data;
5. read the perf CSR snapshot through MMIO;
6. let `soc_cpu_tb` emit the existing CSR-sourced `PERF_JOB`.

No generic command-list executor is required in the first patch. If the first
Transformer report shows launch/control overhead dominates, command-list or
layout support becomes an evidence-backed hardware/software extension.

### 3.4 What Perf Report Should Preserve

`sw/tools/perf/report.py` already groups jobs by generated manifest `job_id`.
Transformer support should extend, not replace, this behavior.

Perf report should preserve:

```text
scenario
logical_op
logical_shape
rtl_tile_shape
precision
activity_scope
external_memory
job count
total cycles
core matmul cycles
data mover words/read_words/write_words
```

This lets one report answer:

- how many descriptor jobs a logical Transformer workload required;
- whether prefill and decode are being compared separately;
- whether measured on-chip movement differs from modeled external traffic;
- whether the current array is poorly utilized by decode-shaped work.

### 3.5 What PPA Proxy Should Validate

`sw/tools/ppa/proxy_report.py` should still use measured CSR-sourced RTL
performance for cycles and on-chip movement.

For Transformer workloads, PPA proxy should additionally report modeled
external-memory events from manifest metadata:

```text
on-chip proxy energy:
  measured matmul/core/data-mover events

external-memory proxy energy:
  activation_read_bytes
  activation_write_bytes
  weight_read_bytes
  kv_cache_read_bytes
  kv_cache_write_bytes
```

The PPA output should verify and expose:

| Question | Evidence in report |
| --- | --- |
| Is this prefill or decode? | `scenario` |
| What logical shape was evaluated? | `logical_shape` |
| What did current RTL actually execute? | job count, op, tile shape, measured cycles |
| How much on-chip movement happened? | CSR data mover read/write words |
| How much external memory is modeled? | manifest external-memory bytes |
| Is external energy measured or modeled? | separate `modeled_external_memory` contribution |
| Are two reports comparable? | matching `workload_manifest_id` and schema |

Important rule:

```text
Do not merge modeled external-memory energy into measured on-chip RTL energy
without labeling it separately.
```

## 4. Verification Scope / 最后 PPA 测试验证什么

The first Transformer PPA validation is not a hardware-speedup proof. It is a
contract and evidence-chain validation.

It should prove:

1. The Transformer source spec is parseable and has required fields.
2. Prefill and decode workloads are distinct in manifest/report/PPA output.
3. Generated INT8 inputs and weights produce expected INT32 golden outputs.
4. Firmware launches the generated descriptor jobs with generated `JOB_ID_*`.
5. `PERF_JOB` records still come from firmware-read perf CSR snapshots.
6. `perf.json` carries Transformer metadata and measured cycle/movement data.
7. `ppa_proxy.json` carries both measured on-chip proxy events and separately
   labeled external-memory model events.
8. Existing CNN/MNIST workload groups remain present and passing.

In the first successful report, the useful architecture output should be:

```text
prefill projection:
  cycles, job count, core matmul cycles, data mover words, proxy energy

decode skinny m8_compat:
  cycles, job count, useful logical MACs, tile occupancy / utilization proxy,
  data mover words, proxy energy

KV-cache traffic:
  modeled bytes/token and modeled external-memory proxy energy
```

This evidence is then used to decide the first real Transformer-driven RTL
extension.

## 5. Implementation Priority / 实现步骤优先级

### P0: Tighten The Source Spec

Update:

```text
workloads/manifests/transformer/transformer_micro_v0.jsonc
```

Required changes:

- make `precision` explicit per workload or inherit from a documented default;
- add `activity_scope`;
- add `external_memory` fields, even when values are zero;
- choose first exact executable shapes small enough for default regression;
- keep KV-cache traffic as `model_only_initially`.

Acceptance:

- unit test validates required fields;
- manifest still distinguishes `transformer_prefill` and `transformer_decode`.

### P1: Add Transformer Fixture/Golden Generator

Add:

```text
sw/tools/transformer/golden.py
sw/tools/transformer/generate_transformer_micro_fixtures.py
```

Responsibilities:

- parse `transformer_micro_v0.jsonc`;
- generate deterministic INT8 A/B tensors;
- tile logical GEMM into current `8x8x8` / K-stream-compatible chunks;
- compute INT32 golden C;
- return firmware arrays and manifest metadata.

Acceptance:

- Python unit tests compare generated golden output against independent matmul;
- no external model/data dependency.

### P2: Connect Generator To Firmware Data Emission

Update:

```text
sw/tools/firmware/emit_soc_cpu_smoke_data.py
```

Responsibilities:

- call Transformer generator;
- append generated C arrays/constants;
- append generated `JOB_ID_*` values;
- append Transformer jobs and metadata to `build/perf/workload_manifest.json`.

Acceptance:

- generated manifest contains existing CNN jobs plus Transformer jobs;
- job ids are unique and match firmware constants;
- existing tests for CNN manifest counts are updated deliberately.

### P3: Launch Transformer Jobs In Firmware

Update:

```text
sw/soc_cpu/apps/soc_cpu_smoke/main.c
```

Responsibilities:

- stage Transformer generated arrays;
- launch existing matmul/K-stream descriptors;
- check output against golden data;
- keep CSR perf snapshot reads unchanged.

Acceptance:

- `make cpu-soc-sim` passes with Transformer workloads enabled;
- existing CNN/MNIST checks still pass.

### P4: Extend Perf Report Metadata

Update:

```text
sw/tools/perf/report.py
test/rtl/test_perf_report.py
```

Responsibilities:

- preserve Transformer workload metadata into `perf.json`;
- show scenario/shape/precision/external-memory fields in report summaries;
- reject Transformer jobs without explicit manifest identity.

Acceptance:

- unit test verifies metadata survives manifest -> perf report;
- no order-based inference is used for Transformer workloads.

### P5: Extend PPA Proxy For External-Memory Model Events

Update:

```text
sw/tools/ppa/proxy_report.py
ppa/schema/ppa_proxy_report.schema.json
test/ppa_contract/test_ppa_contract.py
```

Responsibilities:

- keep measured on-chip proxy events as today;
- add separately labeled modeled external-memory byte events;
- include external-memory energy contribution using configured coefficients;
- keep comparison compatibility checks based on workload manifest identity.

Acceptance:

- PPA contract test verifies external-memory events are separate from measured
  on-chip events;
- `make ppa-l0-report` passes;
- report labels external-memory energy as modeled, not measured RTL power.

### P6: Decide First RTL Extension From Evidence

Only after P0-P5 produce a useful report, choose hardware work.

Candidate decisions:

| Evidence | Possible next extension |
| --- | --- |
| too many repeated descriptors / staging cycles | command-list or tensor-layout support |
| decode `m8_compat` has poor useful-MAC utilization | skinny-GEMM/GEMV valid-row/valid-column support |
| KV-cache modeled energy dominates | external-memory/KV-cache accounting or movement interface |
| tiny block blocked by missing vector ops | RMSNorm/reduction/SFU pipeline work |

## 6. Review Checklist

Before coding, review should settle:

1. Exact first executable shapes for prefill projection and decode skinny
   `m8_compat`.
2. Whether Transformer micro workloads are enabled by default or behind a make
   variable for the first implementation.
3. Whether generated Transformer arrays stay inside `soc_cpu_smoke_data.h` or
   split into `transformer_micro_data.h`.
4. Whether model-only KV-cache traffic appears in the main `ppa_proxy.json`
   immediately or in a separate Transformer analysis section first.

## 7. Implementation Status / 实现状态

Status after the first implementation:

- source spec: `workloads/manifests/transformer/transformer_micro_v0.jsonc`
  now carries executable tiny prefill/decode shapes, `activity_scope`, and
  explicit external-memory fields;
- generator: `sw/tools/transformer/generate_transformer_micro_fixtures.py`
  reads the spec and generates deterministic INT8 K-stream fixtures and INT32
  golden outputs using `sw/tools/transformer/golden.py`;
- firmware data: `sw/tools/firmware/emit_soc_cpu_smoke_data.py` remains the
  `soc_cpu_smoke` aggregation point and now appends Transformer arrays,
  `JOB_ID_*` values, executable manifest jobs, and model-only KV-cache
  metadata;
- firmware execution: `sw/soc_cpu/apps/soc_cpu_smoke/main.c` launches two
  current-RTL-compatible Transformer K-stream jobs after the existing
  smoke/CNN workloads;
- perf report: `sw/tools/perf/report.py` preserves Transformer metadata and
  carries model-only workload entries separately from executable job counts;
- PPA proxy: `sw/tools/ppa/proxy_report.py` reports modeled external-memory
  bytes separately from measured on-chip RTL events.

当前第一版实现结果：

- 原始 spec 已包含 tiny prefill/decode 可执行 shape、`activity_scope` 和显式
  external-memory 字段；
- 新增 Transformer fixture/golden 生成器，生成确定性的 INT8 K-stream 输入和
  INT32 golden；
- `emit_soc_cpu_smoke_data.py` 只做聚合，合并 Transformer 产物到固件 header 和
  production manifest；
- firmware 在现有 smoke/CNN workload 后运行两个 Transformer K-stream job；
- perf report 保留 Transformer metadata，并把 model-only KV-cache 条目与真实
  executable job count 分开；
- PPA proxy 把 measured on-chip events 和 modeled external-memory contribution
  分开报告。

Implemented executable micro workloads:

| Workload | Shape | K chunks | Measured cycles | Core matmul cycles | Data mover words |
| --- | ---: | ---: | ---: | ---: | ---: |
| `transformer_prefill_gemm_tiny` | `8x8x16` | 2 | 118 | 20 | 336 |
| `transformer_decode_skinny_gemm_m8_compat` | `8x8x8` | 1 | 84 | 10 | 208 |

Model-only workload:

| Workload | Modeled external bytes | Purpose |
| --- | ---: | --- |
| `transformer_kv_cache_traffic_tiny` | 131584 | decode KV-cache read/write external-memory pressure |

The generated production manifest id for the quick profile is now:

```text
soc_cpu_smoke_quick_v0
```

The all-profile manifest id is `soc_cpu_smoke_all_v0`. These intentionally
differ from the previous `soc_cpu_smoke_v0` baseline manifest. Existing Level 0
baseline comparison is therefore marked incomparable until a matching frozen
baseline is reviewed.

Validation:

```text
PYTHONPATH=sw/tools python -m unittest test.rtl.test_transformer_micro_fixtures test.rtl.test_perf_report -v: PASS
make cpu-soc-quick: PASS, 20 descriptor jobs including Transformer job_id 19/20
make ppa-l0-report: PASS
make test: PASS, 51 tests, 25.605s
git diff --check: PASS
```

The long real-MNIST CNN full-`fc1` regression is no longer part of the default
quick firmware profile. Use `make cpu-soc-cnn-full`, `make cpu-soc-all`, or
`make test-full` when the full CNN path is the intended gate.
